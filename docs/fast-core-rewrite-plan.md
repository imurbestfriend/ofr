# Переписывание конвейера с приоритетом скорости

Статус: план; реализация нового конвейера еще не начата.

Ветка: `codex/fast-core-rewrite`.
Базовый коммит: `96d9cea` (`main` на момент создания ветки).

Этот документ задает направление новой ветки вместо прежнего плана
`console-readiness-plan.md`. Приоритеты пользователя изменены: скорость первого
анализа важнее исчерпывающего извлечения и сохранения всех особенностей прежнего
конвейера. Исходный интерфейс — консоль и `reports/<Компания>/` — сохраняется.
Кэширование остается последним этапом.

## 1. Что именно строим

Одна команда формирует краткий финансовый анализ компании по локальным PDF.
Результат содержит доступные ключевые показатели за последний найденный отчетный
период, сопоставимые предыдущие значения и ссылки на конкретные документы.

Обычный запуск должен быть пригоден для ожидания у терминала: целевой диапазон
60–180 секунд на отчетах с качественным текстовым слоем. Это проверяемая
инженерная цель, а не уже достигнутое время и не обещание для любого API или PDF.

Скрипт намеренно не исследует каждый показатель каждого документа. Он выбирает
наиболее полезные свидетельства и работает в пределах бюджета. Если данных мало,
результат становится короче, а не запускает неограниченный поиск и уточнения.

Сначала делаем короткий измеримый прототип. Расширение продукта начинается только
после проверки времени и качества на СИБУРе и НОВАТЭКе.

## 2. Объем обычного результата

### 2.1. Финансовое ядро

Ориентир — 15–20 основных финансовых показателей и до 5–10 полезных дополнительных
показателей. Это верхний ориентир, а не требование обязательно заполнить 30 строк.

Приоритет: выручка, операционная прибыль, чистая прибыль, EBITDA при раскрытии,
денежный поток от операций, инвестиции/капитальные затраты при однозначном
раскрытии, денежные средства, долг при однозначном составе, активы, обязательства,
капитал, дивиденды. Дополнительно — несколько явно подписанных операционных
показателей, если они находятся в отобранных сводках.

Показатели определяются доступными источниками. EBITDA не подменяется операционной
прибылью, инвестиционный денежный поток не объявляется CAPEX, отсутствующее
значение не превращается в ноль. Расширенные методики долга, FCF, LTM и отраслевые
расчеты не входят в первую версию. Общая выручка и выручка сегмента различаются.

Первоначально показывать раскрытые показатели. Изменение между двумя значениями
можно считать программно только для сопоставимых периодов, единиц и периметров,
при ненулевой базе; отрицательная база требует явного правила или отсутствия
процентного изменения. Произвольные аналитические формулы пока не нужны.

### 2.2. Периоды

Основной период — последний подтвержденный период отчетности, а не последний год,
встреченный в тексте. Предыдущие значения брать из сопоставимых колонок того же
отчета, если они есть. Для потоков сохранять длительность периода; для балансовых
показателей — дату состояния. Полугодие не сравнивать с полным годом как одинаковые
периоды. Несколько периодов могут использовать разные исходные PDF.

Если выбор периода неоднозначен, показать это в результате. Не выполнять отдельный
модельный поиск всех исторических значений ради заполнения сравнительной колонки.

### 2.3. Excel

Основной лист `Анализ`: показатель, период/дата, значение, единица, сопоставимое
значение при наличии, источник и краткое пояснение. Если сравнительные значения
имеют разные источники, хранить ссылки для каждого значения отдельно.

Документ, физическая страница и цитата должны быть доступны у каждого принятого
значения. Второй лист `Проверка` содержит неоднозначности, недоступные разделы,
пропуски из-за лимита и сводку охвата документов. Допускается другая компактная
компоновка, если она не дублирует все данные и сохраняет проверяемость источников.

Краткую сводку формировать шаблоном из принятых значений. Отдельный запрос модели
на красивое заключение не нужен для первого рабочего результата.

## 3. Что убираем из обязательного запуска

- Полное извлечение всех количественных упоминаний со всех страниц.
- Воспроизведение всех строк всех финансовых форм МСФО.
- Подробную генерацию рисков, мер минимизации и отдельного заключения по рискам.
- Описание бизнеса и отрасли из RA Expert, обновление внешних источников.
- Поиск всех экологических целей, технологических возможностей и прогнозов.
- Обязательный OCR каждого скана, анализ всех изображений и векторных элементов.
- Многоступенчатое восстановление больших JSON с глубоким разбиением задач.
- Автоматический переход к старому полному конвейеру при недостатке данных.

Это осознанное уменьшение объема результата. В частности, наличие ссылок не
означает, что проверены все страницы документа. Пропущенные данные и границы
обработки должны быть видны пользователю.

Полный режим и возвращение дополнительных разделов не входят в первую поставку.
Сначала подтверждается полезность быстрого ядра; каждое последующее расширение
должно укладываться в согласованный бюджет времени.

## 4. Минимальные правила достоверности

Пользователь разрешил упрощение тонкостей, поэтому новые проверки не должны
воспроизводить всю сложность прежнего валидатора. Оставляем короткий обязательный
набор, который предотвращает явную дезинформацию:

1. Принятое число и единица подтверждаются выбранным исходным фрагментом.
2. Файл и страница берутся из локально извлеченных данных, а не из придуманной
   моделью ссылки. Цитата восстанавливается из исходного фрагмента.
3. Сохраняются знак, множитель и очевидное ограничение; нормализация не меняет
   исходную запись. Сомнительный разделитель или сноска не исправляются догадкой.
4. Год, период и дата состояния соответствуют заголовку/колонке источника.
5. Явно обозначенные цели, прогнозы и мощности проектов не выдаются за результаты
   компании. В первой версии такие записи можно исключать из финансового ядра.
6. Очевидная сегментная/дочерняя принадлежность не превращается в показатель
   группы. При неопределенности значение помечается или не включается в сводку.
7. Отсутствие данных, ноль и ошибка запроса остаются разными состояниями.

Уточнения тонких отраслевых классификаций, полная геометрическая проверка всех
подписей и восстановление далеко расположенных сносок остаются за пределами MVP.
Известная проблема в выбранном ключевом значении решается точечной проверкой
источника в пределах бюджета либо явной отметкой; не запускается анализ всего PDF.

## 5. Новый путь данных

```text
reports/<Компания>/*.pdf
  → локальный текст по страницам
  → выбор отчетного периода и релевантных страниц
  → компактный пакет свидетельств
  → 1–2 ограниченных запроса извлечения
  → короткая программная проверка
  → до 1 дополнительного запроса при необходимости
  → Excel + журнал времени и покрытия
```

### Шаг A. Локальное чтение

- Один пакетный вызов `pdftotext -layout` на документ, разделение по страницам.
- Наличие и число страниц проверяются локально; текст привязан к исходному пути.
- Сохраняются номера строк и контекст заголовков, доступный в текстовом слое.
- Не получать координаты, изображения и векторные данные для всего корпуса.
- Титульные/заглавные страницы использовать для определения документа и периода.
- Сканы/плохой текст отмечать сразу. Без достаточного текста быстрый запуск
  возвращает понятное ограничение; массовый OCR автоматически не включается.
- На прототипе не вводить тяжелые зависимости и не строить отдельную базу знаний.

### Шаг B. Выбор свидетельств

- Локально искать основные формы, ключевые финансовые сводки, сравнительные
  колонки и краткие операционные итоги по структуре, заголовкам, единицам и
  числовому наполнению. Название компании не должно определять правила отбора.
- Для каждой категории ограничить число кандидатов; приоритет у последнего
  подтвержденного отчета и его сравнительных колонок.
- Включать нужное начало таблицы и соседний контекст. Не добавлять соседнюю
  страницу автоматически к каждой странице.
- Начальный экспериментальный лимит — 8–16 целевых страниц и до примерно
  60–100 тысяч символов свидетельств. Точные значения уточняются измерением
  контекста модели и полноты на контрольных отчетах.
- Не требовать исключить все дубли эвристикой до модели. Убирать только
  очевидные повторения, сохраняя идентичность документов и периодов.
- Кандидаты, не вошедшие в бюджет, отражаются в сводке охвата.

### Шаг C. Извлечение

- Один основной запрос на финансовое ядро. Второй независимый запрос допускается
  для дополнительных показателей или отдельного блока источников.
- Небольшой фиксированный JSON, ограниченное число показателей и короткие
  пояснения. Модель возвращает идентификатор свидетельства для каждого значения.
- Не просить модель писать полные цитаты/пути и длинный текст, если их можно
  достать программно из возвращенного идентификатора.
- Для выбранных сложных страниц допустим адресный bbox/рендер. Это дополнение
  к нескольким свидетельствам, а не обязательный проход по каждой странице.
- Использовать текущий настроенный API первым. Сравнение других моделей может
  быть отдельным экспериментом после получения замера; ускорение не основывается
  на предположении о доступности новой модели.

### Шаг D. Проверка и запись

- Выполнить минимальные проверки раздела 4 и локальную сборку источников.
- Один дополнительный запрос возможен только для существенного пробела или
  исправимого сбоя и только при оставшемся бюджете.
- Неразрешенные значения не заполнять догадкой. Короткий отчет с понятными
  пробелами предпочтительнее долгого бесконечного дозаполнения.
- Записать временную книгу, открыть ее и проверить, затем опубликовать результат.
- Сохранить журнал и сводку текущего запуска; не использовать их в следующем.

## 6. Бюджет времени и работы

Начальные настройки прототипа подлежат замеру:

| Ограничение | Начальный ориентир |
|---|---|
| Нормальные запросы анализа | 1–2 |
| Дополнительное уточнение | не более 1 |
| Всего API-попыток, включая повторы | не более 4 |
| Параллельных запросов | до 2; `-w` остается верхним пользовательским ограничением |
| Ожидание одного запроса | ориентир до 45–60 секунд, ограниченный общим остатком времени |
| Бюджет всего запуска | по умолчанию 180 секунд, включая подготовку, запросы и запись |
| Целевое время на текстовых PDF | 60–180 секунд |

Один механизм управляет повторами и тайм-аутами; скрытое умножение повторов SDK
и прикладного кода исключается. Время для валидации и сохранения резервируется
до отправки последнего запроса. У каждого subprocess также есть срок ожидания.

Бюджет в 180 секунд ограничивает работу, но не гарантирует полноценный результат.
Если к сроку есть полезные проверенные данные, сохранить отчет с явным состоянием
`частично`. Если данных нет, завершить с понятной ошибкой. Полнота ограниченного
быстрого режима и успешность технического выполнения — разные характеристики.

При Ctrl+C не запускать новые задачи и не выдавать прерванный запуск за успешный.
Уже отправленный сетевой запрос ограничивается своим тайм-аутом. Увеличение
параллельности не должно быть главным способом ускорения.

## 7. Устройство кода

Новая реализация не импортирует старый `analyze_output.py` ради основных шагов.
Логику проектируем заново с небольшими обязанностями и простой моделью данных.
Проверенные короткие функции нормализации можно переносить отдельно вместе
с их тестами, если это ускоряет создание прототипа и не тянет старую архитектуру.

Предлагаемое размещение (модули создавать по необходимости, а не заранее):

```text
pipeline.py                  # совместимый консольный вход
fast_analysis/
    types.py                 # Page, Evidence, Metric, RunStats
    ingest.py                # локальное чтение PDF
    select.py                # выбор периода и свидетельств
    llm.py                   # короткая схема ответа и общий бюджет запросов
    validate.py              # минимальные проверки и источники
    excel.py                 # компактный отчет
    runner.py                # последовательность этапов, время и прогресс
tests/fast_analysis/         # самостоятельные тесты нового контракта
```

Не вводить сервер, API сервиса, брокер задач, БД, RAG/векторную базу,
многоагентную схему, плагины, универсальный workflow-движок и отдельную систему
фоновых заданий. Скрипт должен запускаться одним Python-процессом из консоли.

Модель `Metric` минимальна: название, период/дата, исходное значение, единица,
идентификатор свидетельства, статус/признак проверки и причина при необходимости.
Файл, страница и цитата восстанавливаются по свидетельству. Поля добавляются
по конкретной потребности, а не для сохранения каждого старого сценария.

## 8. Совместимость и консоль

Сохранить папку `reports`, позиционные пути PDF/папок, `--company`, `-o`, `-w`.
Входы должны относиться к одной компании; соседние папки не объединяются молча.
`--company` в новом ядре служит указанием анализируемой компании. Старую связь
этого параметра с обязательным выбором RA Expert убрать из обычного анализа
и явно описать изменение в справке.

`--no-raexpert` можно оставить как совместимый аргумент: внешние описания и так
не входят в новое ядро. Явное использование `--raexpert-dir` должно давать
понятное сообщение об изменении режима, а не создавать впечатление, что досье
использовано. Дополнительные режимы RA Expert пока не реализуются.

Возможные новые необязательные ключи — только по нуждам прототипа:
`--time-budget`, `--max-pages`, `--check`. Значения по умолчанию должны позволять
обычный запуск без подбора десятка настроек.

Консоль показывает: документы и страницы, выбранный период, число отобранных
страниц, число запросов, текущий этап, истекшее время и итоговые ограничения.
Разделить завершенные задачи и начатые запросы. Журнал писать автоматически;
ключи API не выводить. Отсутствующие настройки обнаруживать до анализа.

Никакого скрытого автоматического запуска старого длительного пути. Если выбранный
пакет не дает достаточно данных, это видно пользователю сразу в результате.

## 9. Последовательность реализации

### Поставка 0. Зафиксировать новый контракт

- Закрепить данный объем MVP и признаки `успешно`, `частично`, `ошибка`.
- Зафиксировать 10–15 ключевых контрольных значений для СИБУРа и НОВАТЭКа.
- Выбрать документы, страницы и сопоставимые периоды для ручной проверки.
- Описать список ожидаемых отсутствий: риск-разделы, полные формы, отраслевые
  описания и цели в новое финансовое ядро не входят.
- Проверить рабочую папку перед реализацией: прежние изменения многочисленны
  и не закоммичены; переносить только отобранный код и тесты, не документы,
  ключи, журналы, промежуточные ответы API и результаты.

Готовность: есть четкая короткая спецификация и набор проверяемых результатов.

### Поставка 1. Измеримый прототип

- Реальное чтение всех входных PDF одним локальным проходом на документ.
- Локальный выбор свидетельств и один основной реальный запрос.
- Минимальная проверка и компактный Excel с документами, страницами и цитатами.
- Таймеры этапов, число API-попыток и общий срок работы.
- Прогоны СИБУРа и НОВАТЭКа без чтения прежних результатов.

Первый рабочий замер — ориентир первых 1–2 рабочих дней после начала реализации,
а не после построения всей инфраструктуры. Срок зависит от ответа текущего API.

Готовность: получен полезный реальный отчет и измерено время. Если время велико,
сначала сокращается объем выбранного ввода/вывода, исследуется задержка API.
Полный универсальный разбор таблиц на этом этапе не строится.

### Поставка 2. Ограничения, качество и предсказуемые ошибки

- Не более 4 API-попыток на запуск; общий бюджет 180 секунд.
- Точные источники и проверки чисел, периодов, единиц и явных неверных статусов.
- Одна адресная проверка существенных проблем при оставшемся бюджете.
- Ошибки ключа/баланса, 429, тайм-аут, плохой JSON и отсутствие текстового слоя.
- Сохранение полезного частичного результата и корректные коды завершения.

Готовность: не возникает неограниченного восстановления и ложного сообщения
об успешном полном извлечении. Реальные источники совпадают с принятыми значениями.

### Поставка 3. Проверка на других компаниях и удобство

- Проверить еще минимум две компании из других отраслей и английский отчет.
- Проверить папки с несколькими периодами, повторяющиеся числа, пробелы и кириллицу.
- Уточнить локальный выбор свидетельств, не добавляя правил на имя эмитента.
- Проверить прогресс, --help, установку, запуск, прерывание и открытие результата.
- Обновить краткую инструкцию под новый результат и ограничения.

Готовность: новый пользователь получает полезный отчет по одной команде,
понимает его границы и может открыть источник конкретного значения.

### Поставка 4. Переключение основного входа

- Перевести `pipeline.py` на новый runner после приемки прототипа.
- Предыдущую реализацию сохранять в истории Git; решение об отдельной legacy-
  команде принять только при реальной потребности, не поддерживать две системы
  автоматически.
- Не удалять текущие пользовательские файлы и не перезаписывать исходные PDF.
- Полный набор прежних тестов оценивать по старому контракту: часть функций
  намеренно не входит в новую версию. Сохранить полезные регрессии для нового
  контракта и документировать исключенные режимы, а не объявлять старый набор
  зеленым после скрытого отключения тестов.

Готовность: обычная команда использует только быстрый конвейер. Протокол приемки
показывает фактическое время, объем результата и оставшиеся ограничения.

### Поставка 5. Кэширование

Только после предыдущих поставок: повторное использование локального извлечения
и модельных результатов по содержимому PDF, модели и версии логики. Отдельно
измерить первый и повторный запуск. До этой поставки ускорение обязано работать
без кэша и без возобновления из файлов прежнего запуска.

## 10. Проверка результата и критерии решения

### Скорость

- Измерять весь запуск от команды до сохраненного Excel, включая локальную
  подготовку, ответы API, повторы и экспорт.
- Основные сравнения — одинаковые входы, модель, endpoint, лимиты и параллельность.
- Цель: 60–180 секунд для текстовых контрольных отчетов; общий бюджет по
  умолчанию 180 секунд. Наличие лимита не заменяет получение полезных данных.
- Публиковать фактическое число запросов и время каждого этапа.
- Не засчитывать пустой/неполезный частичный отчет как достижение скорости.

### Качество

- Для каждого контрольного отчета сохраняется согласованное финансовое ядро
  из 10–15 доступных ключевых значений с правильными знаками, единицами,
  периодами и источниками. Полнота по всем показателям документа не требуется.
- Пропущенное ключевое значение учитывается как потеря качества, а не исчезает
  из знаменателя; неправильное значение считается ошибкой даже при верной ссылке.
- Явные прогнозы/цели не становятся фактом. Грубая ошибка принадлежности
  группе/сегменту не принимается ради скорости.
- Допускается меньше дополнительных показателей, больше явно обозначенных
  пробелов и отсутствие редких тонкостей, если ключевые значения проверяемы.

### Тесты

- Локальные тесты отбора страниц, выбора периода, чисел, единиц и ссылок.
- Сквозные тесты настоящего PDF до Excel с заменой только API-транспорта.
- Проверка бюджета с управляемыми часами, без многоминутных ожиданий в тестах.
- Тесты ошибок и частичного результата, сохранения старого файла и отмены.
- Обязательные реальные API-прогоны: замена транспорта в тесте не доказывает
  реальное время и качество модели.

### Решение после прототипа

1. Полезное ядро укладывается в бюджет: доводить устойчивость и переключать CLI.
2. Отбор быстрый, API медленный: уменьшать вход/вывод и испытывать более быстрые
   доступные настройки/модель на тех же контрольных значениях.
3. Быстро, но теряются важные факты: корректировать локальный отбор и точечные
   проверки, не возвращаться автоматически к анализу всех страниц.
4. Нужное качество и время несовместимы на текущем API: показать фактические
   замеры и предложить конкретное уменьшение объема или иной API. Не обещать
   недоказанные сроки и не увеличивать бюджет молча.

## 11. Ближайший следующий шаг

Начать с самостоятельного прототипа нового reader → selector → extraction →
Excel. Получить первый реальный результат СИБУРа с одним основным запросом,
записать время и вручную сверить финансовое ядро. До этого не строить большой
универсальный фреймворк и не переносить всю сложность прежнего проекта.

В рамках текущего запроса создана ветка и подготовлен план. Полное переписывание,
изменение обычного запуска и платные модельные прогоны начнутся отдельным этапом.
